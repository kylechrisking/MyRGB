# Vanguard Pro 96 LCD — how images get onto the screen

Worked out on 2026-11-14 by reading CORSAIR Web Hub (`https://www.corsair.com/web-hub/`), the
browser app Corsair ships for the Vanguard series. It drives the keyboard over WebHID, so its
JavaScript bundle contains the whole command set. **No USB capture was needed**, and iCUE isn't
installed on this PC, so `LCD-CAPTURE.txt` is now only a fallback for confirming details on the wire.

Both the **read** and the **write** paths are confirmed on the real keyboard. On 2026-11-14 a 248 × 170
test card was uploaded and showed correctly: right colors, right way up. See "Probe results" and
"First upload" below. Items still marked **(unverified)** are inferred from the code.

## What the screen is

- Web Hub's device table gives the Vanguard Pro 96 (`1b1c:2b0e`, "K70 Wired Magnetic-Mechanical")
  a `ScreenService`. Its screen-properties call returns **248 × 170**, not the 320 × 170 the
  marketing says. A 248 × 170 image fills it as expected (confirmed 2026-11-14).
- The screen is **not streamed**. Web Hub writes image *files* into the keyboard's onboard
  storage and points the active profile at them; the keyboard firmware then shows them by itself
  in hardware mode. Live widgets (clock, CPU temp) are an iCUE-only feature and use a protocol that
  isn't in Web Hub.
- So the first version of "MyRGB on your LCD" is: **pick an image or GIF, upload it once, and the
  keyboard shows it** even with MyRGB closed. Anything live would mean rewriting flash every few
  seconds, which wears it out. Don't build that on this mechanism.

## Packet framing

It's the same Bragi framing `Bragi.cs` already uses: a 4-byte header
`<subdevice> 01 <session> <command>` and then the arguments. (Web Hub's 4-byte header is our
`00 01 <target> <command>`, with the report id in front.)

| Command | Value | Args | Already in `Bragi.cs` |
|---|---|---|---|
| Set property | `0x01` | `u16 prop LE`, `u32 value LE` | yes (`Set`) |
| Get property | `0x02` | `u16 prop LE` | yes (`Get`) |
| Unbind buffer(s) | `0x05` | `count`, `buffer…` | yes, as `Close` (`05 01 <handle>`) |
| Write begin | `0x06` | `buffer`, `u32 total length LE`, first data chunk | yes, used for colors (`Write`) |
| Write continue | `0x07` | `buffer`, next data chunk | yes (`FileWrite`) |
| Read buffer | `0x08` | `buffer` | yes (`Read`) |
| Describe buffer | `0x09` | `buffer` → reply data `[2..6)` is the file size, u32 LE | yes (`Describe`) |
| Create file | `0x0B` | `u16 fileId LE` | yes (`Create`) |
| Delete file | `0x0C` | `u16 fileId LE` | yes (`Delete`) |
| Open file | `0x0D` | `buffer`, `u16 fileId LE` | yes (`Open`, used with resource `0x22`) |
| Session | `0x1B` | open `01 <token>` / close `02 00 00 00 00 <s>` | yes |

A "buffer" is the handle slot. Web Hub uses buffer 0 (`Common_File_Index`) for file I/O, and
`Bragi.cs` uses handle 1 for lighting. **Use buffer 0 for files so the lighting handle is never
disturbed.** **(unverified that the two can be open at once)**

### Reading a file
1. `0x0D` open `buffer, fileId`. If status is "invalid state", unbind the buffer and retry once.
   Any other failure means the file doesn't exist.
2. `0x09` describe → total size.
3. `0x08` read, repeating until `size` bytes have arrived. Each reply carries one chunk.
4. `0x05` unbind the buffer (always, even on failure).

### Writing a file
1. Open it. If that fails: unbind, `0x0B` create, then open again.
2. `0x06` write begin: `buffer`, `u32 total`, then as much data as fits.
3. `0x07` write continue for the rest. A continue chunk carries 4 bytes more than the begin
   chunk, because it has no length field.
   Chunk size = input report size − header (4) − 5. With 1024-byte reports that's 1015 for the
   first chunk and 1019 after. **(unverified: check the report count on the vendor interface)**
4. Unbind the buffer.

Write-begin is the same command (`0x06`) as a lighting frame, so their replies look alike.
`CorsairKeyboard.WriteFileAsync` skips lighting frames while a file write is running, so a late
frame reply can't be read as a write reply.

Put the whole thing between `Set(prop 0x03 mode) = 2` (host controlled) and `= 1` (self operated).
`Bragi.cs` already does this as `PropertyMode`, `ModeSoftware`, `ModeHardware`.

## Properties

| Property | Id | Meaning |
|---|---|---|
| Operating mode | `0x03` | 1 = self operated, 2 = host controlled |
| Free storage | `62` (`0x3E`) | bytes free for files. Web Hub keeps 5 MiB in reserve on every model except product ids 11012, 11034 and 11099 (the Vanguard is 11022), so an upload must fit in `free − 5 MiB` |
| Screen index | `263` (`0x107`) | which entry of row 0 of the profile's screen layout is shown. **Get property rejects it**; it lives in the profile's *properties file* (below) and is changed by rewriting that file |

## Files

File ids are u16. The ones the host makes come from the range **28000–32767**. Web Hub tracks the
ids it has used in its own browser database, never asks the device, and skips 28049. **MyRGB
should read the device's maps instead of guessing**: walk the screen resource map and the
profile files, then pick an unused id.

### Screen resource map: file `61`
A registry of every image resource.
```
u16 header | u16 count | count × { u16 resourceId, u16 resourceAddress, u8[4] hash }
```
Web Hub sets `resourceAddress = resourceId` and `hash = 00 00 00 00` for new entries. A slot whose
`resourceId` is 0 is empty.

### Image resource (a static image)
```
48 00 | BMP file | u32 unix time LE
```
`0x48` (72) marks a BMP. This is the exact layout from the Vanguard's own `ScreenService`
(lazy-loaded chunk `Dde8HGGV.js`; the main bundle's 24-bit `convertToBMP` is the generic one and
not used here). `ScreenFiles.BuildStaticImage` reproduces it byte for byte, quirks included:

- Every header offset counts from the `48`, not from `BM`: `48 00 'B' 'M'`, then at 4 the total
  file size (prefix and timestamp included), at 12 the pixel offset **54**, at 16 a 40-byte
  BITMAPINFOHEADER: width 248, height **+170**, 1 plane, **16 bpp, compression 3**, image size,
  2835 px/m twice.
- The RGB565 masks `F800 / 07E0 / 001F` are written at 56–67, and then the **pixels are written from
  54 on top of them**. So the file doesn't really carry masks, and the firmware just reads RGB565
  from absolute byte 54.
- The height is positive, which would mean bottom-up, but **rows are written top-down**, and the
  firmware shows them top-down. (Confirmed: the test card's white square is top-left, and red is on top.)
- A pixel is `(R>>3)<<11 | (G>>2)<<5 | B>>3`, u16 little-endian. 248 × 2 = 496 bytes per row, which
  is already a multiple of 4, so there's no padding. (Web Hub's padding loop has a bug, but it
  never runs at this width.)
- After the pixels come **two zero bytes**, then the u32 unix time. The total is 84,380 bytes.

### GIF resource
```
45 00 | raw .gif bytes | u32 unix time LE
```
`0x45` (69) marks a GIF. Web Hub's *animated* path doesn't store the GIF, though. It splits it
into frames, writes each frame as its own BMP resource, and then writes a GIF-config file:
```
u16 0x0066 (102) LE | u16 frame delay ms | u16 frameCount | frameCount × u16 resourceId
```
All the frame resources go into map file 61.

### Screen config (what a layout entry points at, for a static image)
16 bytes: `38 00` (56), `u16 resourceId LE`, then zeros.

### What's showing: file `62`
**The screen shows whatever config is in file 62.** Web Hub's `selectWidget(C)` reads config file
**C** and writes its bytes into file 62 (then sets the screen index, skipped at 0). Adding an entry
to the layout does **not** change the screen; this file does. Web Hub's UI calls it
(`changeScreenWidget`) right after every successful upload, outside the upload function itself,
which is why the first upload attempt showed nothing. On this keyboard file 62 was `38 00 00 00`
beforehand: a static config with resource 0, meaning "no custom image". File 62 is unrelated to
*property* 62 (free storage).

### Profile → screen layout
- The profiles-list file holds `u16 header | u16 count | count × u16 profileFileId`.
- Each profile file has a fixed layout. Its last field, `screenModesLayoutFile`, is a u16 file id
  that comes right after the variable-length name (offsets: 30–31 = name length *n*, name at
  32…32+n, then four u16s, and the fourth is the screen layout file).
  **(unverified: the profiles-list file id is not pinned down yet)**
- Screen modes layout file:
  ```
  u16 header (0x0037 = 55) | u8 rowCount | rowCount × { u8 count, count × u16 configFileId }
  ```
  Web Hub only ever uses row 0. Adding an image appends its *config* file id to row 0.

### Profile properties file
The profile file's fixed fields start `u16 profile | u32 cookie | u16 assignmentsFile |
u16 propertiesFile | …`, so the properties file id is at **bytes 8–9** (Web Hub's
`setDefaultProfileFile` field order; on this keyboard it is 28001).
```
u16 header (0xD43D = 54333) | u16 count | count × { u16 propertyId, u32 value }   (all LE)
```
(Web Hub: `convertBytesToPropertyPair` / `convertPropertyMapToBytes`, used by
`PropertyMapService.updatePropertyProfile`.) Web Hub reads the whole file into an id → value map,
changes the entries it wants, and writes the whole file back with `writeFile` (open, or create and
open, then write-begin with the full length). Colors are stored as `B G R 00`.

Web Hub rewrites the entries **sorted by id**, but the keyboard's own file is not sorted (see the
probe results below). `ScreenFiles.WithProperty` replaces a value in place instead, so setting the
screen index changes only those 4 bytes and leaves the rest exactly as the firmware wrote it.

## Web Hub's sequence for one static image

1. Mode → host controlled.
2. Check that the image fits in free storage (property 62) minus 5 MiB.
3. Pick two unused ids: **R** for the image resource and **C** for its config.
4. Read map file 61, append `{R, R, 0}`, and write it back.
5. Write config file **C** = `38 00 <R> 00…` (16 bytes).
6. Append **C** to row 0 of the active profile's screen-modes layout file.
7. Set the screen index (property 263) to **C**'s position in row 0, by rewriting the profile's
   properties file with that one value changed. **Web Hub skips this when the position is 0**
   (`if(!i) return`, and 0 is falsy). The first image lands at 0, and the index is already 0 on
   this keyboard, so the properties file is left alone.
8. Write image file **R** = `48 00 + RGB565 BMP 248×170 + timestamp`.
9. Mode → self operated (in a `finally`).
10. **The UI then calls `changeScreenWidget(C)`: copy config C into file 62.** Without this step the
    image is stored but never shown.

Web Hub also bumps the profile file's u32 cookie (bytes 2–5) to the current unix time afterwards,
but only when its own browser database has a cookie for that profile. It looks like a change
marker for other hosts, so MyRGB skips it and leaves the profile file alone. The firmware
doesn't need it: the first upload showed without it.

Two Web Hub bugs MyRGB works around:
- The layout parser gives a zero-row layout (`37 00 00`, how this keyboard ships) no
  `rowLayouts[0]`, so Web Hub's step 6 would throw **after** steps 4–5 had already written the map
  and config. MyRGB creates row 0 instead: `37 00 01 01 <C>`.
- The map parser reads the count from byte 4 instead of bytes 2–3. It's harmless on an empty map,
  but MyRGB reads the u16 at 2.

### MyRGB's upload (`ScreenUpload`)
`ScreenUpload.UploadStaticImageAsync` follows steps 2–8 and 10 in Web Hub's order (step 10 is
`ScreenUpload.ShowAsync`). Before the first write, it reads and checks everything, picks the ids,
and saves the map, layout and properties files plus an `upload.txt` manifest to a backup folder.
`ShowAsync` adds file 62's old contents to the same backup. New ids are the lowest ones from 28000 up (not 28049)
that **don't exist on the keyboard** (open fails) and that **no profile, profiles-list or layout
file mentions**: a profile can point at a file that hasn't been made yet. It refuses if the
keyboard has more than one profile, since MyRGB doesn't read the active one yet.
`ScreenUpload.RollBackAsync` writes the saved files back and deletes the new ones.

Live tests (close MyRGB first; both WRITE to the keyboard):
- `MyRGB.Tests.exe -explicit only -method MyRGB.Tests.LiveCorsairLcdTests.Uploads_test_image`
  puts up a test card: red/green/blue thirds top to bottom, with a white square top-left, so both
  color order and orientation show. It then reads every written file back. The backup goes to
  `artifacts/lcd-upload/<time>/`.
- `…LiveCorsairLcdTests.Shows_last_upload` writes file 62 for the newest upload. It's only needed for
  uploads made before the upload did that itself.
- `…LiveCorsairLcdTests.Rolls_back_last_upload` undoes the newest upload that hasn't been undone,
  restoring file 62 as well.

### First upload (2026-11-14, `artifacts/lcd-upload/20261114-103934/`)
- **Ids:** resource **28013**, config **28014**. Neither existed, and the profile doesn't name them.
- **Writes:** map 61 became `44 00 01 00 6D 6D 6D 6D 00 00 00 00`, layout 28006 became
  `37 00 01 01 6E 6D`, the screen index stayed at 0, and the image is 84,380 bytes. Every file read
  back identical.
- **Free storage** dropped 98,304 bytes for an 84,380-byte image, so space goes in 4 KiB blocks.
- **Nothing showed** until file 62 was written. After that the test card appeared, with correct
  colors and orientation. The image appeared with the keyboard in self-operated mode (MyRGB closed).
- **It goes away once MyRGB takes the keyboard (mode 2, host controlled).** The firmware only shows
  stored screens in self-operated mode. Web Hub never shows a screen in host mode: it only switches
  to host mode around file operations and always returns to self-operated in a `finally`.
- **Mode 6 (`LIMITED_HOST_CONTROLLER` in Web Hub's enum, never used there) is rejected** by
  Set property on this keyboard (explicit test `Tries_limited_host_mode`). Modes 3–5 and 7 are
  bootloader, sleep and esports, so they're no help.
- Properties 230/231/232 (Web Hub's `getSupportModules`) only report which modules exist (230 =
  screen present, 232 = wireless). 240 = startup animation active, 242/243 = width/height. None
  hands the screen back to the firmware.

So with MyRGB driving the lights, the screen is the host's. Showing anything on it there means
streaming frames the way iCUE does in software mode, and Web Hub has no code for that. Finding it
needs the USB capture in `LCD-CAPTURE.txt` (iCUE plus USBPcap). The fallback is for MyRGB to hand
the keyboard back to self-operated mode whenever a stored image should show, giving up per-key
host lighting while it does.
- The profile cookie wasn't touched, and the firmware didn't need it.

## In the app (2026-11-15): the fallback, as an opt-in switch

The Devices page has a screen panel on the keyboard's row (`IScreenDevice` in MyRGB.Core,
implemented by `CorsairKeyboard`, view model `ScreenViewModel`):
- **Choose picture…** fits the picture to 248×170 (centered crop, never stretched; `ScreenFit.Cover`,
  transparency comes out black), then uploads it with `ScreenUpload`. **One MyRGB picture at a time:**
  if one is already stored, it is rolled back first, then the new one goes up. If an upload fails part
  way, what it wrote is rolled back.
- The backup of the upload now on the keyboard lives in
  `%APPDATA%\MyRGB\screens\corsair-keyboard\current\` (same layout as `artifacts/lcd-upload/<time>/`).
  It existing is what "a picture is stored" means to the app. **Remove** rolls it back and deletes it.
  A preview PNG sits next to it in `screens\`.
- **Show the screen** (off by default, saved in `ScreenFirstDevices`, re-applied when the keyboard is
  found again) closes the lighting handle and sets mode 1, so the stored picture shows and the
  keyboard runs its own effect. Off: mode 2 and the lighting handle again. While it's on, uploads and
  rollbacks switch to mode 2 around the file writes and back afterwards, as Web Hub does.
- Not yet run on the keyboard: explicit test `Screen_first_round_trip` covers the switch (close MyRGB
  first). The first attempt (2026-11-15, 01:00) ran while an elevated MyRGB still held the keyboard,
  which the test can't stop, so it proved nothing. In that run a Get of property 3 got no reply.
- The test card from 2026-11-14 predates the app; its backup was copied into the app's `current\`
  folder, so **Remove** (or the next picture) puts the keyboard back to how it was before it.

## Probe results (2026-11-14)

`MyRGB.Tests.exe -explicit only -method MyRGB.Tests.LiveCorsairLcdTests.Probes_screen_files`
(close MyRGB first). It is read-only, takes about half a second, and saves every file it reads to
`artifacts/lcd-probe/<time>/`. The first run's copies are in `artifacts/lcd-probe/20261114-004901/`.

- **The read path works as described.** Open on buffer 0, describe, read, unbind. The session's vid/pid
  and mode (2, software) came back as expected.
- **Buffer 0 can be open while lighting handle 1 is open.** The probe runs on the same session MyRGB
  uses, with lighting open. So file I/O doesn't need its own session, though the lighting loop
  should still pause during an upload so the two don't interleave.
- **Free storage (62): 33,243,136 bytes (~31.7 MiB).** After the 5 MiB reserve that leaves ~26 MiB, which
  is about 300 static 248×170 images.
- **Profiles list (file 15):** header `0x0013`, one profile: **28000** "VANGUARD PRO 96 Default
  Profile 1". The profile-file offsets are confirmed: name length, name, then the screen layout
  file **28006**. The profile's properties file is **28001**, at bytes 8–9.
- **Screen layout (28006) is `37 00 00`: zero rows.** Web Hub appends to `rowLayouts[0]` without
  checking, so on this keyboard **the first upload has to create row 0** (`37 00 01 01 <C>`) instead
  of appending.
- **Resource map (61) is `44 00 00 00`:** header `0x0044` and no entries. No custom images are stored,
  so the screen is only showing the firmware's built-in modes.
- **The screen index (263) can't be read with Get property: the keyboard rejects it.** That matches
  Web Hub, which writes it into the profile's properties file (28001) instead.
- **Properties file (28001), second run (`artifacts/lcd-probe/20261114-102936/`):** 94 bytes,
  header `0xD43D`, 15 entries, every one parsed. **263 is already present with value 0**, and 262
  is next to it (also 0), so setting the index is a value change, not an insert. Entries in file
  order: 73=`FFFFFF00`, 74=1, 93=`0000FF00`, 94=`FFFFFF00`, 207=`FFFFFF00`, 4=0, 214=0, 108=0,
  251=0, 252=1, 253=`00BEFF00`, 254=4, 255=7, 262=0, 263=0. They are **not sorted by id**, so a
  Web Hub-style rewrite would reorder them. A parse-then-rebuild in file order reproduces the file
  byte for byte (unit test `Real_properties_file_round_trips_unchanged` holds the real bytes).

## Open questions before writing anything to the keyboard

1. ~~The properties file format (28001).~~ Solved 2026-11-14: see "Profile properties file". Still
   open: whether the firmware cares about entry order (MyRGB keeps the keyboard's order, so it
   doesn't need to find out).
2. ~~Whether the firmware shows an image as the only row-0 entry with the index left at 0.~~ It
   does, once file 62 points at its config.
3. Error cases: a full map file, a full flash, and what the screen does with a malformed BMP.
   The firmware could reject it or hang, so test with Web Hub's exact byte layout first.
4. Rolling back: the probe's saved copies of 61, 28006 and 28001 are what an "undo" writes back.
   A rollback writes those three plus deletes the new files with `0x0C`.

The writes change the keyboard's stored profile. Before the first upload, read the profile's
layout and map files and **save copies to disk** so they can be written back.
